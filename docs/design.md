# はいチーズ！ノート 自動送信管理画面 実装仕様書

作成: 2026-09-16 / 状態: ユーザーとの機能合意済み・Claude Codeへ実装引き継ぎ / 範囲: 既存ツールへのWeb管理画面追加

## 1. 目的

現在は送信内容がPythonコード、送信時刻と停止状態がcronに分かれ、ユーザーが設定を確認・変更できない。ブラウザで現在の設定、次回送信予定、直近の結果を確認し、停止・再開と送信内容を変更できるようにする。
対象リポジトリは `/Users/yasuyuki/Developer/haicheese`。今回は仕様書のみを作成した。アプリ実装、cron変更、送信再開、本番送信は行っていない。

## 2. 誰が、いつ、何に感動するか

既存ツールを利用している本人が、設定確認時やプール期間の開始・終了時にブラウザから使う。スマホ中心でMacでも操作できる画面にする。利用者の追加や複数アカウント対応は今回扱わない。
感動する瞬間: 「画面を開けば停止中か次回いつ送るかが分かり、再開日や体温の範囲を変更すると、その設定どおりに自動送信される。」

## 3. やらないこと

- 登園日・欠席日を登録する画面、日付別の出欠カレンダーは作らない。
- 体温の実測入力や未入力による保留には変更しない。ユーザー指定範囲のランダム生成を維持する。
- Discord専用の通知時刻、7:00固定通知、予定通知は追加しない。送信成功・失敗に連動する既存通知を維持する。
- 「今すぐ送信」、自動再送、複数園児対応、一般公開、別のフロントエンド基盤への全面移行は対象外。

## 4. 受け入れ条件

1. 初回導入時は停止中で起動し、開始日・終了日は未設定、送信07:00、検温06:50、体温36.5〜36.8℃、プール参加を表示する。開始日を勝手に2027年7月へ設定しない。
2. 保存して再読込・サービス再起動しても設定が残る。保存失敗時は以前の設定を維持し、画面に失敗を表示する。
3. 自動送信の有効・無効と開始日・終了日から、停止中・開始待ち・稼働中・期間終了を正しく表示する。初日・最終日を対象に含める。
4. 保存済み設定に基づく次回送信日時を表示する。停止中・期間終了・期間内に対象日がない場合は、予定なしと理由を表示する。
5. 体温の下限・上限を0.1℃単位で指定でき、両端を含む範囲内の値だけを生成する。上下限が等しい場合も動く。上下逆転・不正値・送信先で選べない値は保存できない。
6. プールの参加・不参加と検温時刻を保存でき、その値が送信フォームに反映される。不参加の送信先の値は実際の選択肢で確認する。
7. 送信時刻を例として07:00から08:15へ変更した場合、07:00には送信せず08:15に送信判定する。Discord成功通知は送信完了後に届く。
8. 土日祝日と既存の `skip_dates.txt` 指定日は従来どおり送信しない。これらを画面で編集する機能は追加しない。
9. 同時起動・同日の再起動・時刻の変更でも成功済みの日は再送信しない。送信先が送信済みなら正常なスキップとして記録する。
10. 設定上の有効状態と実際の動作異常を区別できる。直近結果には日時・結果・送信内容または理由を表示し、通信失敗を成功として扱わない。
11. 停止中・開始前・対象外の日には未送信警告を出さない。有効な送信予定を20分過ぎても完了を確認できなければ警告する。変更後の時刻に追従する。
12. 320px・390px・1024px幅で横スクロールがなく、保存・停止を操作できる。未保存の変更と保存済み状態を見分けられる。
13. テストでは時計・送信先・通知先を置き換え、本番送信やDiscord送信なしで上記を検証する。本番の停止状態を維持したまま導入確認できる。

## 5. 画面と操作

画面は1ページとし、上から現在の状態、送信期間、送信内容、送信時刻、直近の結果を並べる。停止操作は常に見える位置に置き、一般の設定保存と区別する。

```text
はいチーズ！ノート
[停止中]                         [自動送信を停止]
次回送信：予定なし（停止中）
動作確認：未確認／正常／要確認

自動送信       [無効／有効]
開始日         [未設定／日付]   終了日 [未設定／日付]
体温の範囲     [36.5] 〜 [36.8] ℃（範囲内でランダム）
検温時刻       [06:50]
プール         [参加／不参加]
送信時刻       [07:00]
Discord通知    送信完了・失敗時に通知

直近の結果     日時／送信済み・失敗・スキップ等／内容・理由
[変更内容の要約]                  [設定を保存]
```

未設定の開始日は日付による開始制限なし、未設定の終了日は期限なしとする。有効にして保存すると対象期間と時刻に従って送信が始まることを、保存前の要約で明示する。開始日が終了日より後なら保存できない。
停止は即時に保存し、未保存の他項目は巻き込まない。開始済みの処理には送信確定前に停止を確認させる。既に送信確定へ進んだ処理は取り消せないため、停止後も結果が届く場合があることを処理中表示で伝える。
保存後にサーバーが返す確定設定と次回予定を表示する。ブラウザで計算した予定だけを確定表示に使わない。複数タブからの古い設定の上書きは更新番号で検出し、再読込を促す。

デザインの参照元は `/Users/yasuyuki/Developer/kintetsu-bot/templates/index.html` と同リポジトリの `docs/design.md`。既存の色・余白・入力欄・ボタンを流用し、参照元アプリ自体は変更しない。
背景 `#f5f4f0`、文字 `#243c48`、補助文字 `#66767d`、罫線 `#e5e7e4`、アクセント `#a46d46` を基本にする。白いカード、システムフォント、スマホで押しやすい操作部、明確なフォーカスを使う。飾りのコピーや英語見出しは追加しない。

## 6. 技術構成とデータ

以下は合意済みの機能を満たすための実装案。既存構成に合わせたファイル名等の調整は可能だが、状態判定・重複防止・停止状態の維持を省かない。

| 項目 | 実装案と理由 |
|---|---|
| 送信処理 | 既存Python / Playwrightの `submit.py` を利用し、固定値を設定値へ置き換える |
| Web | FlaskとHTML/CSS/最小限のJavaScript。個人用の設定画面として構成を小さくする |
| データ | `data/app.sqlite3` に設定と実行記録を保存し、トランザクションで更新する |
| 定期実行 | OSから毎分起動する判定処理。Webプロセス内のタイマーには依存させない |
| 監視 | 送信処理とは別の定期チェック。固定07:20とログの有無だけによる判定を置き換える |
| 日時 | サーバーで `Asia/Tokyo` に統一。ブラウザ端末のタイムゾーンに依存させない |

設定は `enabled`、任意の `start_date/end_date`（YYYY-MM-DD）、`submit_time/measurement_time`（HH:MM）、`temp_min/temp_max`、`pool_participation`、更新日時、更新番号を持つ。体温は内部では0.1℃単位の整数で扱い、浮動小数の誤差を避ける。
実行記録は対象日、予定時刻、開始・終了時刻、設定のスナップショット、今回生成した体温、結果、理由、通知結果を持つ。送信成功・送信先で送信済み・失敗・結果不明を区別し、通知失敗によって送信成功を失敗へ戻さない。予定判定とUI表示は同じ関数を使う。
毎分の判定は、対象日かつ設定時刻の分だけ送信を開始する。過去時刻への変更やMac停止中の予定を後から即時送信しない。予定を過ぎて実行されなかった日は未実行として表示し、20分後の監視対象にする。同日に将来時刻へ変更した場合も成功済み・結果不明なら再送しない。
送信開始前に排他制御と対象日の実行記録を確保する。同時実行を防ぎ、異常終了後に送信結果が不明な記録を自動再試行しない。送信確定前には停止状態を再確認する。その他の設定変更は開始済みの処理を途中変更せず、次回の処理へ反映する。
`GET /api/status` は確定設定・運用状態・動作状態・次回予定・直近結果を返す。`PUT /api/settings` は全項目を検証して原子的に保存し、`POST /api/pause` は停止だけを保存する。実際のAPI構成は同等の振る舞いなら調整可能。
導入時は既存の送信・監視ジョブを確認し、旧ジョブと新ジョブを重複稼働させない。初期状態を無効のまま移行する。`skip_dates.txt` は保持し、READMEの古いパスと体温範囲も実装内容に合わせて直す。

## 7. 秘密情報と失敗したとき

既存 `.env` の資格情報を継続利用し、ブラウザ・APIレスポンス・ログへ返さない。`.env`、`data/`、ログ、スクリーンショット等の個人データはGit管理から除外する。設定変更APIには認証とCSRF対策を設け、一般公開しない。スマホからの接続は既存の近鉄アプリのTailscale限定運用を参照する。
設定の検証失敗・DB読取失敗・設定欠落時には送信せず、画面へ理由を表示する。送信ボタンを押せたことだけでは成功にせず、送信先の完了表示を確認して成功を記録する。タイムアウト等で確定できない場合は「結果不明」とし、自動再送を止める。
送信の成功・失敗通知は既存のDiscord・Mac通知を維持する。通知だけ失敗した場合は送信結果と分けて保存・表示する。監視は失敗済み・結果不明と未実行を区別し、同じ予定について毎分通知を繰り返さない。
実装完了時は、変更ファイル・検証結果・未確認点・起動と停止の手順を報告する。本番への送信、Discordの実送信、運用再開、外部公開、pushは実施直前に対象と影響を示して本人に確認する。現在の停止を勝手に解除しない。

## 8. わかっていないこと・実装時の確認

コードで確認した現状は `submit.py` の体温36.5〜36.8℃、検温06:50、プール参加固定、土日祝日と `skip_dates.txt` の除外、送信後通知。READMEには古い体温範囲とパスが残っている。運用ノートでは2026-09-12から送信・監視とも停止中、再開は2027年7月頃で具体日は未定。
今回の環境では `crontab -l` が権限エラーで読めず、実際のジョブ登録状態は未確認。Claude Codeは導入前に現在のcron・実行Python・常駐方式・ポートを確認し、他のジョブを保持すること。
送信先の体温の選択可能範囲・刻み、検温時刻の選択肢、不参加の値、確実な完了表示は未確認。フォームの選択肢に合わせて検証を実装し、本番への送信を伴わない調査・fixtureで確認する。医学的な閾値を独自に追加しない。
Webの待受ポート、スマホからのアクセスURL、認証の具体方式は既存環境に合わせて実装時に決める。近鉄アプリの認証情報自体は流用しない。接続できないときは古い稼働表示を正常と見せず、情報取得失敗を表示する。
